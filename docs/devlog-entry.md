# MusicSync：把「我喜欢」的歌自动补齐到本地

一个小工具：定时读你在音乐平台的歌单，跟本地曲库比一遍，缺哪首补哪首。Windows 和 macOS 都能跑。

## 为什么做这个东西

我的歌单一直在长，本地曲库一直没跟上。每次想起来手动点一遍，都是同一套动作：翻歌单、找哪首没下过、切平台、重命名。做过三次之后就烦了，索性让它自己干。

最初的版本只有一个 `netease.py` 和一个 `while` 循环。后来把「跑完给我个提示」也加上了，因为最难受的不是下载慢，是不确定它到底跑没跑。再后来有人问能不能换成别的平台，就有了第二、第三个适配器。

## 它现在能做什么

- 读歌单、对账、补缺，已有的直接跳过
- 每个平台可以填自己的歌单，留空就自动按名字找账号里的「我喜欢」
- 三个平台可选做主来源，主平台没有版权的歌可以换源补
- 不用填任何凭证：网易云直接读客户端本地登录态，其它平台读浏览器里已经登录过的状态，一键就好
- 注册系统定时任务（Windows 计划任务 / macOS launchd），每周 / 每天 / 每隔 N 小时跑一次；跑完右下角弹个小窗汇报结果
- 自动把网易云、QQ音乐客户端里的下载成品归到曲库目录
- 平台不给原生音源（VIP / 版权限制）时，把客户端里下载到的加密音频（`.ncm` / `.qmc*` / `.kgm`）在本机还原成普通 mp3 / flac，一起参与对账
- 一条命令自检：依赖、目录、网络、登录态、计划任务，哪里缺了都会说

## 下载与使用

（占位：GitHub Releases 页面和安装说明补齐后替换。）

大致三步：装好运行环境 → 跑 `python -m music_sync settings` 填一遍 → 用 `scripts/install_task.ps1`（Windows）或 `scripts/install_task.sh`（macOS）注册定时任务。README 里有完整步骤和每个平台拿登录态的办法。

## 几个值得说的实现

**多平台适配器架构。** 每个平台是一个 `BaseAdapter` 子类，只实现「拉歌单」「取下载地址」两件事，剩下的重试、跳过已存在、失败归集全在 `sync.py` 里统一处理。`platforms/__init__.py` 维护一个注册表，加平台不用改主流程——汽水音乐先只放了占位适配器，也是靠这个结构才敢先占位再补。

**歌名对账算法。** 下载下来的文件按 `歌手 - 歌名.mp3` 命名，对账的时候就按这个格式反解回「歌手 / 歌名」再去歌单里比对。麻烦在于同一首歌在两边可能写成 `周杰伦 - 晴天` 和 `晴天 - 周杰伦`，或者一边带 `(Live)` 一边不带。做法是先把文件名和元数据都拆成候选对，再做规范化（去全半角差异、去多余空白、括号版本词单独提出来当附加特征），只有「歌手+歌名」都能对上且版本特征不冲突才算命中。宁可多下一次，也不要因为模糊匹配把不该下的删掉或者漏掉。

**计划任务和右下角提示窗。** 计划任务用 `schtasks /Create /XML` 注册——不是因为它优雅，是因为 `/SC` 那套开关设不了「工作目录」和「错过就开始」，而这两项缺一个，任务在别的机器上就会跑出怪事。脚本幂等，先删再建，改时间就是重跑一次。提示窗是个独立的 `pythonw.exe` 进程，只活几秒，主同步进程下完就退出，不留常驻后台。

**跨终端自检。** `python -m music_sync check` 把所有「我这里能跑、换台机器就炸」的东西挨个查一遍：Python 版本、依赖能不能 import、曲库目录能不能写、配置里有没有残留的占位值、各平台登录态、计划任务装没装。每项给 `ok / warn / fail` 和一句人话说明。这条命令的用处是省掉「你那边报什么错」这个来回。

**把 Windows 的东西抽出来，才有 macOS。** 1.1.0 最大的工作量不是写新功能，是把原来散在各个文件里的平台假设集中到一处（`ospaths.py`）：配置目录、默认曲库、浏览器数据目录、客户端安装位置，全部按平台分支，别的模块只问它。定时任务同理，抽出 `schedule.py`，对外只有 `install / uninstall / run_now / status` 四个动作，Windows 走 `schtasks`、macOS 走 `launchd`，命令行和自检都用同一份。这样加平台是改一个文件，而不是满仓库找 `sys.platform`。

**macOS 上的登录态是另一套机制。** Windows 读浏览器的登录数据是 DPAPI + AES-GCM；macOS 的密钥在钥匙串里（`security find-generic-password` 取出来做 PBKDF2，1003 轮，再 AES-128-CBC 解）。两套解密逻辑分开写、按平台分发，Windows 那条路径一行没动——这是硬要求，因为它已经在真机上跑了几个月。macOS 多支持了一个 Safari（`Cookies.binarycookies` 二进制格式），虽然它需要「完全磁盘访问权限」，但聊胜于无。

**每个平台可以有各自的歌单，留空就按名字找「我喜欢」。** 1.2.0 之前只有一个全局 `playlist`，四个平台共用同一个歌单 id——问题是各平台的 id 体系根本不通，换了平台就得手动改一遍，忘了就拉到个空歌单。现在配置里是 `platforms.<平台>.playlist`，旧的顶层 `playlist` 降级成兜底值。自动识别的入口在 `BaseAdapter.resolve_playlist()`：先把配置值丢给 `is_auto_playlist()` 判断，它认三种情况——空串（以及 `auto` / `自动` / `默认` / `liked` / `favorite` 这类写法）、去掉空格和 `_-.·` 之后还是空或别名的、以及名字里含 `LIKED_ALIASES` 里任何一个叫法（「我喜欢」「我喜欢的音乐」「喜欢的音乐」「我的喜欢」「我的收藏」「默认收藏」……）。命中就走子类实现的 `find_default_playlist()` 去账号里找，返回 `(歌单 id, 歌单名)` 并记在 `last_playlist_name` 上，日志和提示窗都显示真实歌单名，用户能一眼看出这次拉的是哪一个。找不到就让适配器抛 `PlatformError`，提示语直接告诉用户去设置里填 id——宁可明确报错，也不要悄悄拉个空歌单让人以为工具坏了。每个平台各写各的 `find_default_playlist()`：网易云翻账号歌单列表找 `specialType=5` 的那个特殊歌单；QQ音乐认固定的 `disstid=201`，但会先真拉一次确认能取到曲目再认；酷狗先在账号歌单列表里按名字找，酷狗的默认收藏不是公开歌单、接口拿不到时就明确提示手动填。

**为什么「我喜欢」在每个平台叫法都不一样。** 这东西从来就不是一个统一概念：网易云把它做成账号里的一个特殊歌单（`specialType=5`，名字叫「我喜欢的音乐」）；QQ音乐是固定槽位 `201`，网页版叫「我喜欢」；酷狗是账号下的 `specialid`，界面上写「我喜欢」或者「默认收藏」，而且不对外公开成普通歌单。所以自动识别不能只靠一条字符串，得有别名表 + 每平台自己的查找接口 + 明确的失败提示三层。别名表故意放宽到「名字里包含就算」——用户自己建个叫「我喜欢歌单」的歌单也会被当别名，这是刻意的取舍：多认几个比少认强，真认错了在设置里填个 id 就盖掉了。

**为什么做「加密音频解锁」。** 有些歌平台就是不给普通用户原生 mp3 / flac 直链——VIP 专属、版权限制、接口下架，甚至是歌单里有但搜索接口拿不到地址的那种，工具会把它记成「无版权/下架」跳过。可如果你是付费或有授权的用户，官方客户端里照样能点「下载」，只不过下下来的是加密容器（`.ncm` / `.qmc3` / `.kgm`），只有对应客户端能放。也就是说：文件其实一直拿得到，只是锁着。于是干脆在本地把锁打开——读本地加密文件、在本机算、写成本地普通音频，按文件里带的「歌手 - 歌名」改名放进曲库，再参与对账。顺序上放在对账**之前**，否则刚解锁的文件还没被比对，会再下一遍。全程不联网、不上传，也不碰账号密码；算法来自几个 MIT 开源项目，按算法自己用 Python 重写，没拷贝代码（见 README 的「算法来源与许可」）。目前只有网易云 `.ncm` 在真机上验证过（529 个真实文件，ffmpeg 解码通过），酷狗 `.kgm` 和 QQ `.qmc` 只有算法交叉验证 + 单元测试——本机既没有真实样本，也没装那两个客户端。

**三种加密格式的算法要点。** `.ncm` 是结构最清楚的：文件头有固定魔数 `CTENFDAM`，后面跟两段「先逐字节异或、再 AES-128-ECB 解」的数据——一段是密钥（异或 `0x64`，解出来前 17 字节是前缀、后 16 字节才是真正的 key），一段是元数据（异或 `0x63`，解出来还带着 `163 key(Don't modify):` 前缀和 `music:` 前缀，里面是含歌名歌手的 JSON）。真正的音频流用一把 256 字节 keybox 逐字节异或，keybox 由那把 16 字节密钥喂进 RC4 变体的 KSA 生成。QQ音乐的 QMCv1（`qmc0/qmc2/qmc3/qmcflac/qmcogg`）没有密钥，靠一张 8x7 的静态种子表生成掩码，掩码按「之」字形走位、每 `0x8000` 字节还插两个固定字节（`0xC3` / `0xD8`），所以**掩码和文件偏移强相关，不能只解开头一段**，得整文件流式过。酷狗的 `.kgm` 介于两者之间：16 字节魔数后，`0x10` 处是 headerLen，`0x1C` 处有 16 字节密钥，音频流逐字节做「掩码 ^ 密钥 ^ 密文」；掩码由两层 `16x17` 的表按位置算出来，还带低位异或的收尾处理。新版酷狗换了魔数就是 `.vpr`（同结构、不同魔数），新版 QQ 的 `.mflac/.mgg` 则是 QMCv2 那套密钥体系，目前只认得出、解不开——认得出来就该明确提示，别静默失败。

- 新增「加密音频自动解锁」：把客户端下载的加密容器在本机还原成普通 mp3 / flac，放进曲库并参与对账，全程不联网、不上传

## 说明

- 汽水音乐只有占位适配器，不能登录、不能下载，只占个平台位。
- QQ音乐和酷狗的下载接口我没有在真机账号上完整验证过，是按公开接口写的，接口一变就可能失效。
- 加密音频解锁里，网易云 `.ncm` 在 529 个真实文件上验证过（ffmpeg 解码通过）；酷狗 `.kgm` 和 QQ音乐 `.qmc*` 只有算法交叉验证 + 单元测试——本机没有真实样本，也没装这两个客户端，真机效果以你的日志为准。QQ新版 `.mflac/.mgg`、酷狗 `.kgg`、酷我 `.kwm` 目前只认得出、解不开。
- macOS 支持是 1.1.0 刚加的，Windows 侧是主力开发环境，macOS 侧的关键环节还没在真机跑满，用 `python -m music_sync check` 会逐项告诉你哪里没通。
- 只用来管理自己账号的歌单。

代码不复杂，总共几千行，`music_sync/` 下面按模块拆开了，想改哪个平台直接照 `netease.py` 抄一份就行。
